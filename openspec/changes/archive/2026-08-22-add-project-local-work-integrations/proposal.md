## Why

Forge projects can own MCP servers and other local tooling, but the framework has no portable contract for declaring and safely consuming arbitrary project-specific integrations. It also lacks a work-source profile that can turn heterogeneous Kaiten tickets—or equivalent records from another local source—into Forge Bugs, Epics, and Tasks without coupling the framework to one provider or breaking project customizations during framework upgrades.

## What Changes

- Add an optional, project-owned integration registry for arbitrary local capabilities such as work sources, knowledge sources, data sources, analysis services, and future project-defined types, without making any provider, MCP server, API, or CLI a framework dependency.
- Define capability profiles and explicit consumers: an integration declares semantic operations, scope, access policy, data handling, and platform-local bindings, while a framework or project-owned skill must explicitly declare which capabilities it is allowed to use.
- Add `work_source` as one capability profile, with connector binding, read scope, field mapping, and project-specific label-to-area hints; Kaiten is a local example of this profile rather than a built-in integration.
- Add an external-work intake workflow that can fetch an explicitly selected ticket or a configured candidate queue, normalize source records, and preserve stable source provenance for deduplication and later traceability.
- Maintain explicit many-to-many links from external tickets to Forge Epics and Bugs in `BACKLOG.md` and to Tasks in `execution/`, so the agent can reconstruct source coverage during planning, resume, Replan, implementation, and validation.
- Require the orchestrator to classify ticket intent and granularity before changing canonical state: one ticket may become a Bug, one Epic with later Tasks, multiple Epics, or be combined with related tickets into one Epic.
- Treat labels such as `Расчет запасов`, `UI`, `ИИ агент`, `RAG`, and `Рекомендации по бурению` as project-configured scope hints rather than fixed framework concepts or automatic Epic boundaries.
- Reuse existing feature/bug intake, canonical approval, Replan, Plan Approval, Epic Start, and Task Start gates. External records provide evidence and candidate scope; `SPEC.md`, `ARCHITECTURE.md`, `BACKLOG.md`, ADRs, plans, and TASK files remain authoritative.
- Define safe failure and trust behavior for unavailable connectors, incomplete mappings, malformed records, duplicate imports, and untrusted instructions embedded in external ticket content.
- Add versioned integration schemas and an upgrade compatibility contract that preserves project-owned definitions and state, stages and validates supported schema migrations, isolates unsupported or malformed integrations, and supports rollback without requiring connectors to be online.
- Keep projects with no local integrations behaviorally unchanged. The framework does not generate MCP configuration, install connectors, poll boards in the background, or write status/comments back to the external system in this change.

## Capabilities

### New Capabilities

- `project-local-integrations`: Declares the provider-neutral registry, capability profiles, explicit skill consumers, trust and permission boundaries, runtime discovery, and upgrade compatibility for arbitrary optional project-local integrations.
- `external-work-intake`: Defines retrieval, normalization, classification, grouping, provenance, deduplication, and handoff of external tickets into the existing Forge canonical intake and development lifecycle.

### Modified Capabilities

None.

## Impact

- Framework ownership, conventions, manifest, project configuration template, bootstrap/migration/final-validation guidance, compatibility policy, and adapter synchronization/lock behavior.
- A new portable Forge skill and root-router routing for external work intake, plus updates to feature intake, bug intake, release planning, resume behavior, and user documentation.
- Project-owned integration configuration and provenance state under `.ai/`, plus source references in Backlog and execution artifacts; existing project-owned MCP or connector configuration remains separate and is never generated by Forge.
- Tests and scenarios covering no integrations, arbitrary and unknown capability profiles, platform parity, supported/unsupported schema upgrades, rollback, Kaiten-like heterogeneous tickets, one-to-many and many-to-one Epic classification, duplicate prevention, unavailable tools, and prompt-injection-resistant handling of integration output.
